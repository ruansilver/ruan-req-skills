# 代码核实

本 Reference 说明如何从项目快照形成 Technical Fact，并处理输入更新。不要为了证明一个局部问题而无目的扫描整个仓库。

## 核实路径

从反馈中的页面、文案、错误、接口、数据字段或用户动作开始，沿着实际链路查找：路由/页面 → 组件或控制器 → API/Service → 数据结构和持久化 → 权限与验证 → 状态流、任务和配置 → 相关测试与上下游依赖。

使用 `rg`、项目已有搜索工具或 IDE 索引，优先寻找真实的组件名、方法名、接口名、表名、权限 key 和状态值。先提出“这个事实会改变哪个需求判断”的问题，再读取代码。

## Technical Fact 记录

记录短结论和定位，不复制大量代码。推荐形态：

```markdown
- Fact: 上传接口在校验失败时只返回首个错误字段
  Code reference: src/upload/UploadController.java, `createUpload`
  Relevance: 影响 REQ-003 的错误展示范围
  Uncertainty: 未确认生产环境是否已部署当前快照
```

Technical Fact 描述项目快照内部；生产行为、真实部署、现场流程和外部约束写为 Context Fact。用户提供的日志可以帮助定位，但如果它描述的是快照外环境，仍按 Context Fact 处理。

## 输入更新

用户明确输入已更新时，先记录用户给出的影响范围。使用已有代码路径/符号、REQ `touches` 和 `source_fb` 定位受影响 REQ，然后重新核实关键事实。用户无法说明范围时，优先复核 planning-ready REQ，并在 ENTRY 中留下本轮未覆盖范围。

## 不确定性

代码证据不足时，不用猜测填空。把结论写成“尚未核实”，说明缺失证据和下一步最小核实方向。只有会改变需求方向的缺口才进入用户追问；可由代码继续查明的缺口不转嫁给用户。
