# Ruan Requirement Discovery

## 目标和边界

把零散用户反馈、问题记录、截图、口语化需求或半成品需求材料，转化为可恢复、可推进、受当前代码事实约束的需求收集与需求分析文档。

输入：

- 用户反馈目录：必需。材料可以重复、矛盾、过期、只有截图、只有口语记录或只是临时碎片。
- 需求收集目录：可选。未指定时，在用户反馈目录旁边创建清晰命名的需求收集目录。
- 当前代码库：用于核实现状、技术栈、端类型、核心流程、数据流、状态流、权限模型、UI 结构、模块边界和关键实现路径。

硬边界：

- 不实现需求，不修改业务代码，不把此 Skill 变成后续开发流程规则。
- 此 Skill 的产物是需求实现前的需求收集与分析文档；后续开发应受这些产出的需求文档约束。
- 不迷信已有文档或反馈表述；当前代码是第一事实来源。
- 不要求用户提前整理反馈；先由 Codex 建立索引、归类和核实路径。
- 不用固定大模板压制判断。文件名、目录结构和文档拆分可以按项目习惯选择，但恢复契约不可丢失。

## 必须维护的文档能力

保持文档集小而可恢复。以下是能力要求，不是固定文件名要求；可以合并或拆分，但职责必须清楚，入口文件必须点名恢复所需的少量关键文档。

- 入口控制面板：恢复任务用的单一入口，不是最终报告。持续维护任务目标、输入输出目录、当前进度、已完成范围、未完成范围、当前关键问题、需要用户决策的问题、关键代码事实、冲突、下一步和文档索引。
- 反馈索引：记录反馈来源、归类、状态、重复关系、冲突关系、过期标记、是否已代码核实、是否已需求细化和原始材料追溯。
- 需求收集与分析主文档：维护已细化或阶段性完成的需求项，包括原始意图、代码事实、推荐方向、可选方案、影响范围、难度、风险和仍需确认的问题。
- 用户决策记录：记录用户对迭代方向、取舍、默认偏好、范围边界和重要问题的回答。重要决策不能只留在对话中。
- 当前追问文档：每次需要向用户追问时，清空或归档旧问题后写入本轮问题，并在回复中告知用户文档路径。
- 冲突与全局复盘记录：记录不同反馈、局部方案、模块、流程、数据模型、权限模型、状态流或核心 UI 结构之间的冲突和全局判断。
- 代码事实记录：记录从代码核实得到的关键路径、模块、接口、数据结构、权限逻辑、状态流、实现约束和不确定性。可并入需求主文档，但入口控制面板必须能指到这些事实。
- 后续仍需收集的问题清单：仅在确有必要时保留，说明为什么现在无法完全锁定、开发推进到哪个节点再问、要问什么、不问会有什么风险。

## 恢复契约

每轮开始必须先读入口控制面板。若入口文件不存在，先创建需求收集目录、建立初始反馈索引和入口控制面板，再做深度分析。

入口控制面板必须至少维护：

- 本 Skill 的任务目标和边界。
- 用户反馈目录、需求收集目录、代码库根目录及路径假设。
- 当前进度：索引、代码核实、需求细化、用户追问、全局复盘分别处于什么状态。
- 已处理、处理中、未处理和等待用户确认的反馈范围。
- 当前关键问题、冲突、疑似过期项、风险和全局复盘触发点。
- 关键代码事实摘要，并链接到承载这些事实的文档。
- 已确认用户决策摘要，并链接到用户决策记录。
- 当前追问文档路径及是否需要用户回答。
- 下一轮建议从哪里继续，以及停止点。
- 文档索引：恢复时只需要读取哪些少量关键文档。

每轮结束前必须更新入口控制面板和被它点名的关键文档。不要把恢复状态只留在聊天记录中，也不要让最终报告承担入口控制面板职责。

## 每轮启动方式

在有限上下文下分轮推进，每轮只处理一个主题或一组高度相关的问题。

1. 解析用户反馈目录和需求收集目录；未指定输出目录时，在反馈目录旁边创建。
2. 若已有入口控制面板，先读入口文件，再只读入口文件点名的关键文档。
3. 若没有入口控制面板，先扫描反馈目录并建立反馈索引，不要求用户整理材料。
4. 定位当前代码库根目录；若根目录不明确，记录假设并用最小必要代码事实推进。
5. 识别当前轮需要的技术栈、端类型、核心用户流程、数据流、模块边界和关键实现路径。
6. 根据入口控制面板选择当前轮工作单元，避免一次性铺开全量反馈。
7. 读取当前轮必要的反馈材料和代码，完成核实后及时沉淀结论。

## 处理混乱反馈

反馈索引优先于深度分析。索引不等于最终需求结论，但必须让后续工作知道每条材料在哪里、属于什么问题、处理到哪一步。

- 重复反馈：合并为同一问题组或建立同源关系，保留全部来源，避免重复追问和重复需求项。
- 矛盾反馈：记录冲突内容、来源、可能原因、影响范围和待确认点，不要擅自抹平。
- 明显过期反馈：标记过期原因和依据，不删除原始来源；若只是疑似过期，明确标为待核实。
- 截图反馈：提取可见 UI 状态、文案、数据、路径线索、可能用户动作和可验证假设；需要时使用截图查看或 OCR。
- 口语化或片段反馈：先转成可验证的问题、用户意图、预期结果和当前阻塞，再决定是否需要追问。
- 描述不完整反馈：先通过代码和已有材料补足背景；只有用户意图、业务规则、价值取舍、默认策略或范围边界无法推断时才追问。

可使用适合项目的状态标签，例如：已索引、已归组、重复、冲突、疑似过期、已过期、待代码核实、已代码核实、已细化、待用户确认、后续阶段再确认。不要让状态标签变成僵硬流程。

## 代码核实原则

每处理一组反馈，都要带着具体问题深入代码核实第一事实。

尽量找到：

- 相关组件、页面、路由、接口、服务、状态管理、后台任务、数据结构、权限判断、验证逻辑、文案、测试和配置。
- 反馈对应的类型：bug、体验问题、需求缺失、流程冲突、技术债、文案问题、权限问题、数据模型问题、集成问题或新需求方向。
- 影响的端、模块、用户流程、上下游依赖、数据契约、权限边界、回归面和实现难度。
- 项目已有 UI 组件习惯、设计系统、接口契约、测试习惯、数据模型边界和工程约束。

记录代码事实时使用简短结论和路径引用，不复制大量代码原文。代码事实不足时，明确写出不确定性、缺失证据和下一步核实方向。

涉及前端设计、交互或视觉体验时，优先依据项目已有 UI 约束、设计系统、组件习惯、工程内事实，以及可用的前端或 UI/UX Skill；不要只依赖模型通用审美。

## 需求细化原则

把“用户反馈的问题”转化为“下一版本可落地的需求判断”。每个需求项尽量回答：

- 用户真正遇到的问题是什么。
- 重度使用者可能希望达成的结果是什么。
- 当前代码为什么导致或限制这个问题。
- 推荐解决方向是什么。
- 是否存在多个可选方案，默认推荐哪个，为什么。
- 影响哪些端、模块、流程、数据、权限、UI、用户习惯或开发范围。
- 实现难度、关键风险、回归点和测试关注点在哪里。
- 是否仍需用户确认；若不需要，说明可由代码事实和反馈推断的理由。

默认把本次迭代当作可能的最后一次迭代，不用“后续迭代再说”降低方案质量。只有存在真实开发前置依赖时，才把需求放入后续阶段再确认清单，并写明当前已能确定的部分。

## 追问用户原则

不要把能通过代码核实的问题转嫁给用户。追问前先合并同类问题，控制数量，优先问会改变需求方向、范围或实现方案的问题。

每次追问前必须更新当前追问文档：

- 清空或归档旧问题。
- 写入本轮问题来源、背景、为什么需要确认、推荐选项、默认推荐和影响范围。
- 在给用户的回复中说明当前追问文档路径。

每个问题应包含：

- 背景：来自哪些反馈和代码事实。
- 为什么需要确认：不确认会影响什么判断。
- 推荐选项：给出可选择方案，不只问开放问题。
- 默认推荐：明确 Codex 基于代码和使用场景更推荐哪一项。
- 影响范围：说明影响哪些功能、流程、模块、数据、权限、端或开发范围。

用户回答后，必须更新用户决策记录、受影响的需求项、反馈索引、当前追问文档和入口控制面板。

## 全局复盘

可以先局部推进，但不能只逐个问题局部处理。出现以下情况时，必须触发或记录全局复盘：

- 多个反馈指向同一底层模块。
- 多个需求影响同一交互流程。
- 局部推荐方案互相冲突。
- 代码事实显示可能需要调整数据模型、权限模型、状态流或核心 UI 结构。
- 用户方向性决策开始影响多个问题取舍。
- 某个局部需求单独实现会破坏整体一致性或长期维护性。
- 当前问题已经足够复杂，继续扩大范围会降低恢复质量。
- 某个看似局部的需求实际跨端、跨模块、跨流程或跨数据契约。

全局复盘应写入冲突与全局复盘记录，并在入口控制面板中标出入口。复盘至少说明：涉及的反馈组、共同底层问题、冲突点、候选方向、默认推荐、影响范围、仍需确认的问题和下一轮行动。

## 主动收束

不要追求一轮处理尽可能多的问题。出现以下情况之一时，主动收束并持久化状态：

- 已完成一组问题的代码核实。
- 已形成一批可沉淀的需求结论。
- 已发现跨模块冲突、架构风险或全局复盘触发点。
- 需要用户决策。
- 上下文中积累了较多代码事实、冲突、决策或未沉淀结论。
- 继续探索会导致已有结论无法及时沉淀。
- 当前问题已经足够复杂，继续扩大范围会降低恢复质量。
- 即将进入大范围全局设计，需要先保存阶段性结论。
- 下一轮任务已经明确。

收束前必须更新入口控制面板，写清：

- 本轮处理了什么。
- 新增了哪些代码事实和不确定性。
- 哪些反馈已合并、标记过期、代码核实、需求细化或待确认。
- 当前是否需要用户回答问题，以及当前追问文档在哪里。
- 下一轮应该从哪里继续。
- 恢复时只需要读哪些关键文档。

## 最终文档标准

需求收集与分析文档必须服务于下一版本迭代计划。阶段性或最终整理时，保留未决问题，不要把不确定性伪装成已确认结论。

合格的需求项应尽量覆盖：

- 原始反馈追溯和用户真实意图。
- 已核实代码事实和关键路径。
- 推荐解决方向、可选方案和默认推荐。
- 影响端、模块、流程、数据、权限、UI 和用户习惯。
- 实现难度、风险、冲突、回归点和测试关注点。
- 需要用户决策的问题、已确认的用户决策和后续阶段仍需收集的意图。

每次完成时，向用户简要说明本轮更新了哪些文档、是否需要回答当前追问文档中的问题，以及下一轮建议从哪里继续。不要在最终回复中粘贴完整文档内容。
